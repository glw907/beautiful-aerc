## How to read this report

The report diffs the major mail clients' feature surface against the locked spec. Each capability is marked **covered**, **deferred** (named-deferred in the spec), **weak** (named but underspecified enough that two implementers diverge, or the affordance is missing), or **omitted** (the spec is silent). Gaps are ranked by how load-bearing each is for the coder audience and the better-Pine product. Section 3 is the ranked index. Section 6 carries the per-domain evidence: the field comparison matrix, the spec line, the adversarial-verify result, and the sources. Locked-decision tensions (section 4) are flagged, not resolved. Gap IDs (`G-<domain>-<n>`) are this report's own handle for Pass C to cite.

## 1. Executive summary

The spec is deep and internally coherent inside its seven feature domains. Within a domain it usually matches or leads the field. The gaps cluster in two places: the seams between domains, and the non-functional layer the domain-organized spec has no section for. A fan-out of eight domain surveys plus an adversarial verify stage produced **78 confirmed gaps** and dropped **7 candidates** the spec already covers. **22 of the gaps would reopen a locked decision**; those are flagged for the Pass C gate, not resolved here.

Three of the gaps are correctness bugs in a feature the spec does build, not missing features. Charset and MIME transfer decoding is never named, so the section 4 renderer assumes a UTF-8 text the pipeline never produces, and legacy-charset mailing-list mail and RFC 2047 headers render as mojibake. The invite block shows a fixed local time with no VTIMEZONE or RRULE handling, so a user can RSVP yes and arrive an hour early. The non-OAuth IMAP and SMTP path specifies no TLS-enforcement or STARTTLS-downgrade policy, a security gap for the self-hosting coder the spec courts. These three rank above any absent feature, because a wrong result is worse than a missing one.

Two capabilities look cut by accident rather than by decision. Mouse support is absent from a spec for a bubbletea showcase whose archived code set mouse mode every frame. The logging and observability seam is gone, though "log every user-visible error" is a standing project invariant. Both read as omissions to confirm, not considered cuts. Onboarding is named as first-class yet specifies no connect-test probe, no manual-config fallback, and no autoconfiguration, so the guided flow guides only the OAuth cohort.

The field carries coder-audience features the spec lacks: arbitrary-header search over List-Id and the X-GitHub headers, find-in-message, a bound raw-source key, format=flowed on outbound text, Sieve vacation, contact groups, and a pipe-and-hook extensibility surface. Junk handling has a Disposal destination but no mark-as-junk verb and no sender lists, table stakes across the GUI field. The largest single cluster sits in the cross-cutting layer that no section owns: notifications, accessibility and NO_COLOR, a user-facing CLI surface, backup and at-rest cache encryption, and a performance budget for huge folders. That the layer has no home is itself the structural finding Pass C should weigh.

## 2. Method

Eight subagents surveyed one feature domain each (accounts, organization, reading, rendering, compose, search, contacts, and a cross-cutting non-functional sweep), cataloged the weighted comparators, and classified every capability against the spec with primary-source citations. The comparators are Thunderbird, Apple Mail, Outlook (classic and the new Graph client), mutt and neomutt, aerc, K-9 and Thunderbird for Android, Geary, Evolution, and alpine and pine; the terminal three are the closest analogues. A second adversarial stage tried to refute each claimed gap by grepping the whole spec, including the section 8 consolidation, before it counted; it upheld 78 and dropped 7. FairEmail and niche clients were out of scope per project guidance.

## 4. Locked-decision tensions

A gap whose fix would reopen a decision the charter or the spec locked. Flagged for Geoff's sign-off at the Pass C gate. Pass A neither resolves nor endorses these; it names the decision and the pull against it.

**T-1 (ACC). Backends in v1 are JMAP (Fastmail) and generic IMAP only; no POP3.**

POP3 is still offered by Thunderbird, Apple Mail, classic Outlook, mutt, alpine, and Evolution, and some legacy/cheap hosts are POP3-only. But the two closest terminal analogues weaken the case: aerc has no POP3 backend and isync/mbsync (the standard CLI sync tool coders pair with terminal clients) explicitly does not support POP3. POP3 also has no folders, no server-side flags, and no IDLE, so it fits poorly with the spec's folder-classified, label-capable, push-driven, delta-sync cache model. Adding it would mean a degenerate backend that fails most capability flags.

Reference: §1.3 L58-63, charter §4 'generic IMAP', spec brief 'No POP3'.

**T-2 (ACC). No Exchange/EWS or Microsoft Graph backend.**

Microsoft 365 personal accounts cannot use OAuth over IMAP (Microsoft has stated no plan to add it), and the new Outlook itself routes M365 mailboxes through MAPI/HTTP or Graph, not IMAP. So a Microsoft-mailbox user is effectively unreachable by poplar's IMAP path for personal M365, and entirely unreachable for Exchange-only org mailboxes. The field (classic Outlook, Apple Mail EWS, Evolution EWS, Thunderbird via add-on) serves these.

Reference: §1.3 L58-63; charter scope; spec brief 'no Exchange/EWS/Graph'.

**T-3 (ACC). No local maildir/mbox account model (account is always a network backend; 'No maildir' inherited from legacy invariants).**

The closest analogues lead here: aerc supports maildir, mbox, and notmuch backends; mutt/neomutt are maildir/mbox-native; notmuch is the power-user terminal standard; Evolution has local accounts. A common coder workflow is mbsync/isync pulling IMAP to local maildir, then a terminal client reading the maildir offline. Poplar's cache-as-source-of-truth already gives offline reads, so the offline motivation is partly served, but a user with an existing maildir/notmuch store or an air-gapped archive has no account type for it.

Reference: §1.3 L58-75; legacy invariants 'No maildir'; spec brief 'no local maildir/mbox account'.

**T-4 (ACC). Bring-your-own OAuth client ID for v1; a shipped verified client is deferred post-1.0 (§8.6).**

Every GUI comparator ships its own verified OAuth client, so their Gmail/Microsoft onboarding is email+password+consent with zero developer setup. Poplar's v1 makes the user create a Google Cloud project, configure OAuth consent, and drive it to 'In production' (else 7-day refresh-token expiry with Gmail scopes) before they can read mail. This is a steep first-run wall for the exact Gmail-first majority the product targets, and it directly raises the stakes on the onboarding-flow and autoconfig gaps above (the guided flow must now also teach Google Cloud Console).

Reference: §1.6 L139-149; §8.6 L2079.

**T-5 (ORG). Results, and by extension the folder list, sort by `sent_at` descending with no relevance toggle and no other sort key. The spec locks this in §6.2 and acceptance scenario §6.6.11, citing Geary/K-9/aerc/Apple/Outlook/Fastmail as defaulting to date.**

Adding a sort-by-sender/subject/size/unread verb (gap 5) reopens this locked default. The cited precedent is about the DEFAULT order, but aerc (`:sort` over arrival/cc/date/from/read/size/subject/to) and mutt ($sort/$sort_aux/$sort_thread_groups), the two closest terminal analogues, both make sort a first-class re-orderable operation. So the lock is correct as a default and over-broad as a prohibition. Resolving it means either (a) keeping date-only as a deliberate Pine-simplicity stance and stating that explicitly, or (b) adding a sort picker and re-deriving §6.2 L1465 and scenario §6.6.11.

Reference: §6.2 L1465; §6.6 scenario 11 L1553.

**T-6 (ORG). Threads are account-scoped; the same external conversation on two accounts shows as two rows (§2.1 L267-270), consistent with §1.1's account-partitioned storage where nothing joins across account DBs.**

Cross-folder threading WITHIN one account (gap 7) does not contradict this account-scoping, but the spec's silence sits right against it: the same impulse that keeps threads account-scoped (storage partitioning, folder as a SQL constraint in §6.1) could be read to keep threads folder-scoped too, which would drop a user's own Sent replies from the conversation. Clarifying that intra-account threads span folders (the Gmail/JMAP-threadId behavior) does not reopen the cross-account two-rows decision, but it must be stated without implying cross-account joins.

Reference: §2.1 L267-270; §1.1 L24-26; §6.1 L1398-1400.

**T-7 (ORG). Server-side rules are modeled as a single sentinel-fenced managed Sieve BLOCK, regenerated wholesale, over JMAP Sieve or ManageSieve (§2.4); Gmail filters are deferred (§8.6).**

Adding Sieve vacation (gap 2) collides with this single-managed-block model on JMAP, because RFC 9661 + RFC 8621 make the vacation responder a DISTINCT `VacationResponse` object that may not be content-updated or destroyed through the generic SieveScript/set path the managed block uses. So vacation cannot simply be another action inside the fence on a JMAP backend; it needs a parallel object-shaped path.

Reference: §2.4 L331-349; §8.6 L2070.

**T-8 (RDG). Fixed keyboard map with no user rebinding: one Go key.Binding registry is the single source of truth, the help popover renders from it, a test asserts they cannot drift, and "No separate hand-maintained keybindings document is the source of truth."**

All three terminal analogues poplar weights most (mutt, neomutt, aerc) treat rebinding as a core feature: aerc binds.conf has global/per-context/per-account/per-folder binds with parent-erasure, mutt/neomutt bind+macro remap any function. Closing the customization gap (a [keys] config surface or a user binds file) would reintroduce exactly the second hand-maintained source of truth the spec forbids and would break the help-renders-from-registry test invariant. Naming only; the spec author must decide whether Pine-opinionation outweighs the migrant expectation.

Reference: §8.1 L1906-1913.

**T-9 (RDG). Modifier-free single keys, no multi-key sequences, no `:` command mode, because bubbletea delivers one key event per press.**

Vim-style counts (5j, numeric-prefix jump like mutt) and marks (set then jump) are inherently multi-key sequences, and an interactive sort picker or column chooser as a `:`-style command is exactly the command mode the spec bans. So the count/marks gap and any command-line-driven sort/column control cannot be closed without reopening the no-sequence / no-`:` rule. The select-by-criteria menu (V) and modal pickers are the spec's sanctioned escape hatch; whether sort/columns/counts should ride that same picker idiom or stay omitted is the unresolved tension.

Reference: §3.1 L490-493, §8.1 L1790-1792.

**T-10 (RDG). One pane is the default (Pine lineage); opening a message replaces the list in place, and the only multi-pane affordance is an opt-in right-side widescreen follower preview past ~130 columns.**

Reading-pane orientation choice (Outlook Right/Bottom/Off), horizontal/vertical split (aerc), and tabs / multiple open messages (Thunderbird, aerc) all require either a second pane orientation or a tab/window model that breaks the one-pane-in-place contract and, for tab switching, likely needs chords. Adding bottom-preview or tabs reopens the single-pane decision; the spec presents the right-only follower as the complete multi-pane story without naming these rejected alternatives.

Reference: §3.1 L499-500, §3.2 L548-563.

**T-11 (RND). Modifier-free single keys, no multi-key sequences, no `:` command mode (charter §2; spec §3.1, §8.1 1790-1792)**

Find-in-message, raw-source/headers toggle, and save/export each want a new reader binding, and the reader keymap is already dense (n/N, v/V, g/G, Space, Tab, 1-9, @, U, i, q all taken, with v/V and n/N already context-overloaded). Find-in-message and save-to-path also need a text-entry prompt.

Reference: charter §2 (line 22); spec §8.1 (1790-1864).

**T-12 (RND). Pine-style single-message reader, one message in place of the list (spec §3.5 668-710); threading is a list-side collapse, not a reader-side stack**

Whole-thread stacked rendering (Apple Mail Complete Threads, Geary default, Thunderbird conversation view) is half the weighted field's reading model, and a coder reading a long review thread benefits from continuous scroll over one message. Adding it would change the reader from a single-message surface to a thread surface, touching the §4 render path (render N messages stacked with separators and per-message quote folding), the n/N traversal semantics, mark-read rules, and the preview pane. That is a reader-pane architecture decision, not a §4 rendering tweak.

Reference: charter §2 (line 22); spec §3.5 (668-710), §8.1 reader map (1847-1857).

**T-13 (CMP). Send-side PGP and S/MIME signing/encryption are deferred to a post-1.0 encryption pass; v1 is read-side verify/decrypt only.**

A read-receipt request toggle and an Importance/priority toggle both add a per-message compose-header control surface. That same surface is exactly where a future sign/encrypt toggle lands. Specifying the receipt/priority controls now means designing the compose-options affordance (where per-message header toggles live in the header or a small options row) without the encryption toggle that will share it, risking a second redesign when PGP-send arrives.

Reference: §7.6 lines 1702-1705; deferral register lines 2071-2072; compose header §5.1 lines 1188-1192.

**T-14 (CMP). Tidy folds into catkin and is the only named catkin prose tool; the charter (§8) collapses tidytext into catkin and keeps catkin a poplar-agnostic standalone-spinoff package.**

Closing the spell-check gap means adding a second prose tool to catkin. Spell check is offline, deterministic, and dictionary-based; tidy is online, generative, and provider-gated. Putting spell check in catkin is consistent with the standalone-editor goal (a markdown editor wants a spell checker), but it reopens the question the charter implicitly closed by naming only tidy: which prose tools catkin owns in v1. The tension is scope-of-catkin, not a behavior conflict.

Reference: charter §8 lines 84-86; §5.9 lines 1302-1313.

**T-15 (CMP). The text/plain part is the markdown source, lightly reflowed (§5.5), and text-only mode emits the markdown source verbatim as the wire text so fenced code and diffs pass through unmangled (§5.5 lines 1245-1251).**

Adopting format=flowed (the fix for the reflow gap) collides with the verbatim-passthrough guarantee for code and diffs. format=flowed reflows any line ending in a soft break (trailing space) and space-stuffs lines beginning with space/>/"From ", which would corrupt a unified diff or fenced code block if applied indiscriminately.

Reference: §5.5 lines 1238, 1245-1251.

**T-16 (SRC). Search is local-FTS5-index-ONLY; server search (IMAP SEARCH / JMAP Email/query) is deliberately kept off the read path because it is 'too slow and inconsistent' and a JMAP query is a network hop.**

The two highest-value gaps (server-side fallback for un-backfilled bodies, and arbitrary-header search) are most naturally closed by reaching the server's own search. JMAP Email/query supports text/from/to/cc/bcc/subject/body/header server-side at near-zero marginal cost on the user's primary Fastmail account (RFC 8621 §4.4.1), and IMAP SEARCH / mutt's =b/=B/=h delegate to the server for exactly the incomplete-index case. Closing them requires admitting a server path the charter rule (§1.7 L165-168) forbids on the read path.

Reference: §6.1 L1379-1382, §6.1 L1488, §1.7 L165-168; charter §6 decision 3 (saved searches in scope) and the performance-by-locality rule §1.7.

**T-17 (SRC). Tokenizer is unicode61 with a prefix index and explicitly NO stemming, so code tokens 'match exactly' and recall comes only from the trailing prefix wildcard.**

This same decision blocks substring/infix matching (Handler inside httpHandler) and any regex, which the coder audience needs and which notmuch (the engine both terminal analogues rely on) provides. The FTS5 path to substring matching is the trigram tokenizer, but adopting it changes the locked tokenizer choice and trades index size for infix recall; a secondary trigram index is the compromise but still reopens the L1407-1410 'unicode61 + prefix, exact code tokens' decision.

Reference: §6.1 L1407-1410, §6.4 L1490-1492 (trailing-term prefix wildcard only).

**T-18 (CON). No calendar account model in v1; RSVP sends iMIP METHOD=REPLY only, never reads or writes a calendar.**

The same no-calendar-account decision that defers CalDAV WRITE also forecloses calendar READ, which the spec never names as a consequence. Reading free-busy to warn 'you are already booked at this time' (Evolution/Apple/Outlook all do) and rendering an RRULE/VTIMEZONE invite correctly both touch calendar-domain code that the locked decision pushes out. A coder accepting a recurring cross-timezone invite blind to their own conflicts, possibly seeing a wrong local time, is the cost.

Reference: charter decision 7 (line 71); spec §7.4 1665-1670; §8.6 2073.

**T-19 (CON). PGP/S-MIME default-defer; v1 ships read-side PGP verify+decrypt only, keys from the local GnuPG keyring; S/MIME deferred 'in either direction'; send-side PGP deferred.**

The charter set decision 8 to 'default-defer unless the pass argues otherwise', and the pass argued read-side PGP in but drew two boundaries the field suggests are slightly mis-placed. First, read-side S/MIME VERIFY was folded into the same deferral as send-side, yet its cost profile matches read-side PGP verify (which shipped), not send-side encryption, so 'either direction' over-defers the cheap half.

Reference: charter decision 8 (line 72); spec §7.6 1690-1705; §8.6 2071-2072.

**T-20 (XC). 15 compiled Go themes, One Dark default, no runtime TOML, no glamour (compiled themes as Go values, following Charm convention).**

Closing the user-editable-theme gap (every terminal comparator supports user colorschemes/stylesets: aerc stylesets-dirs, neomutt color + .rc themes, mutt, alpine) requires some runtime theme-loading path, which directly reopens the no-runtime-TOML lock. A reconciliation might be a narrow palette-override file rather than full TOML theming, but any such path crosses the locked line, so it must be a deliberate re-decision, not a build-plan slip.

Reference: charter §4 L46 ('15 themes, One Dark default. No runtime TOML, no glamour'); spec §8.4 and the styling map reference compiled palettes only.

**T-21 (XC). Read state is encoded through brightness, with hue reserved for the cursor and the unread-and-flagged case (a colorblind-aware list design).**

Honoring NO_COLOR or providing a monochrome/no-color fallback (the informal cross-tool accessibility standard) means the brightness-and-reserved-hue scheme must degrade to a color-free encoding of read/unread/flagged/cursor state. That requires a parallel non-color affordance (glyphs/weight) the current design leans on color and brightness for, so adding a NO_COLOR path reopens how read-state and selection are conveyed when color is unavailable. The design is already CVD-leaning, so the tension is specifically the color-absent mode, not hue choice.

Reference: spec §3.4 L626-631 (read-state via brightness, hue reserved for cursor and unread-flagged); no NO_COLOR/monochrome path specced.

**T-22 (XC). Modifier-free single keys, no multi-key sequences, no `:` command mode; text-entry surfaces are the only exemption (the Pine-true keyboard lock).**

Several field-standard extensibility primitives are command-driven: mutt's `|` pipe-message, aerc's `:pipe`/`:exec`, and a save/export/print verb. The keyboard lock does not forbid config-file hooks/triggers (aerc's model is config, not keys) or a single bare-key 'pipe to command' / 'save to disk' action, but it does constrain how a scripting/extensibility surface is exposed interactively.

Reference: spec §3.1 L489-498 and §8.1 L1790-1792 (modifier-free single keys, no `:` command mode).

**G-CMP-1. format=flowed (RFC 3676) on the outbound text/plain part**  (weak, high)

- Spec: §5.5 line 1238 ("Its text/plain half is the markdown source, lightly reflowed"); §4 line 1092 covers the render side only
- Field: mutt ($text_flowed), neomutt, and aerc (format-flowed = true) all emit Content-Type: text/plain; format=flowed with trailing-space soft breaks and space-stuffing; Thunderbird and Evolution emit it by default. The terminal three, poplar's closest analogues, all implement it.
- Why: This is the load-bearing one for the stated audience. §5 line 1143 explicitly targets a user who "sends to mailing lists and patch queues," and RFC 3676 exists precisely to stop the "embarrassing line wrap" that hard-wrapped quoted text/plain produces on reflow. "Lightly reflowed" is ambiguous between (a) hard-wrap to a column, which causes the wrap damage on every downstream reply, and (b) format=flowed soft breaks, which a conforming receiver rewraps cleanly. The spec must pick (b) and name the wire format: trailing-space soft line breaks, space-stuffing of lines beginning with space/>/"From ", and the format=flowed Content-Type parameter, with hard breaks (and DelSp not set) preserved for code blocks and diffs. Without naming it, the implementer will likely hard-wrap, silently regressing the one wire-format detail a patch-sending audience notices.
- Verify: Line 1238: "Its text/plain half is the markdown source, lightly reflowed." That is the only wire-format statement. Grep for flowed/format=flowed/RFC 3676/space-stuff/DelSp finds zero hits on the text/plain side; the RFC 3676 hits at lines 102 and 1230 are the signature "-- \n" separator, unrelated. Reader-side reflow (lines 929, 1092, 1095) is render-only. Genuine weak gap, correctly the highest-stakes one. The spec sets up the patch-queue audience (line 1143, "sends to mailing lists and patch queues") and treats clean text/plain as first-class (line 1144), yet leaves "lightly reflowed" ambiguous between hard-wrap (causes the reflow damage RFC 3676 exists to stop) and format=flowed soft breaks. The spec should name format=flowed: trailing-space soft breaks, space-stuffing, the Content-Type format=flowed parameter, hard breaks preserved (DelSp unset) for code/diffs. Survey's spec ref and rationale are accurate.
