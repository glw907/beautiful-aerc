## 1. OAuth refresh against the #53 lens

The IMAP `dial` path (auth.go:97-113) already implements
`ForceRefresh`-on-`mail.ErrAuth` with a single retry, so a stale
cached access token recovers automatically on cmd-path and
idle-path redials. `mailauth.Client.Token` re-reads the refresh
token from the store on every refresh; the cached access token is
locked behind `c.mu` and zeroed by `ForceRefresh`. The 5-minute
expiry cushion in `Token` (oauth.go:206) keeps the cached value
fresh against `Expiry`-driven rotation.

JMAP does not currently use OAuth — Fastmail authenticates with a
long-lived API token from `cfg.ResolvePassword()`
(jmap.go:178). `classifyErr` routes 401/403 to `mail.ErrAuth`
which surfaces to the user as a banner; no refresh primitive is
needed.

**Finding A (P1).** `mailimap.smtpAuth`
(`internal/mailimap/smtp.go:104-121`) calls
`resolveXOAUTH2SMTPToken` → `b.oauth.Token(ctx)` exactly once. If
the cached access token has been server-side-rotated or revoked
within the 5-minute expiry cushion, `cli.Auth` returns auth
failure and the dial returns the error without consulting
`ForceRefresh`. `Backend.Send` then drops the cached SMTP client
on send error (smtp.go:155) so the next `Send` redials — but
within the cushion window, `Token` still hands back the stale
value, and the next Send fails the same way. Outbox `KindSend`
rows attempt-count toward `OpConflict max-attempts-exceeded`
during the cushion window. **Fix:** mirror the IMAP `dial` pattern
in `smtpAuth` — on `ErrAuth` (after classifying `cli.Auth`'s
error), call `b.oauth.ForceRefresh(ctx)` and retry `cli.Auth`
once. Then drop and redial the SMTP client on the same `ErrAuth`
condition in `Send` so a fresh handle picks up the just-refreshed
token. Queue for Pass 36.1.

**Adjacent observation (P2).** IMAP cmd-path operations
(`actions.go`, `messages.go`, etc.) classify errors via
`classifyErr` and call `maybeDropOnConn` — which only drops on
`mail.ErrConnection`, not `mail.ErrAuth`. A mid-session
`AUTHENTICATIONFAILED` response (rare; most providers close the
connection instead) leaves the cached `b.cmd` handle in place and
surfaces the auth error to the UI. The redial path is reachable
only via connection-dead detection. Not a current-day hazard
(SASL re-auth on a live session is not part of the IMAP cmd-path
contract), but worth a one-line ADR/invariant note if the
remediation pass touches this code.

## 2. Mouse hit-test surface

`App.updateMouse` (app.go:339) computes the sidebar split, Y
bounds, and overlay-absorb gate every frame from current `m.width`
and `m.height` — no cached coordinates survive a `WindowSizeMsg`.
The bounds check `mu.Y < 1 || mu.Y >= 1+m.contentHeight()`
correctly excludes the topLine, the optional chrome banner row,
the status bar, and the footer (chrome budget in `contentHeight`,
app.go:400). `anyOverlayOpen` covers every branch of the View()
overlay cascade — help, confirm, conflict, outbox, link picker,
attach picker, compose attach picker, compose schedule picker,
reschedule picker, move picker, popover-form, popover — and
returns `m, nil` so wheel events on an open overlay don't reach
the viewport behind it.

**Finding B (P1).** When `m.compose != nil` and
`m.viewerOpen == true`, `renderFrame` (app_view.go:51-59) shows
the compose surface in the right pane via
`m.acct.RenderWithRightPane(m.compose.View())`, **but**
`updateMouse` still routes right-pane mouse clicks to the
(invisible-but-still-open) viewer because the conditional is
keyed on `m.viewerOpen`, not on which surface is rendered.
This path is reachable: hitting `r` / `R` / `f` from inside a
ready viewer fires `composeSeedCmd` → `SeededMsg` → `openNewCompose`
(app_compose.go:124-133), which mounts compose but never calls
`m.acct.CloseViewer()`. Hitting `c` while a viewer is open
(app_keys.go:114-123) has the same shape.

Two fixes are coherent — choose one in the remediation pass:

- **Close the viewer on compose open.** Call
  `m.acct = m.acct.CloseViewer()` and re-derive chrome in both
  `openNewCompose` and the `m.keys.Compose` branch of
  `updateGlobalKey`. Matches the rendered state.
- **Route on rendered surface, not on `m.viewerOpen`.**
  Add a `case m.compose != nil:` branch in `updateMouse` ahead
  of the viewer cases, absorbing clicks (or, post-1.0, routing
  to compose for cursor placement). Cleaner contract — `updateMouse`
  consults the same predicate as `renderFrame`.

Queue for Pass 36.1.

## 3. `v.ReportFocus` resume path

The audit-plan focus posits a contract where `tea.BlurMsg` pauses
JMAP push and IMAP IDLE, and `tea.FocusMsg` resumes them. That
contract is **not implemented**. `App.Update` (app.go:277-285)
toggles `m.focused` and clears the new-mail toast on FocusMsg
(per ADR-0217); neither handler returns a tea.Cmd. `pushLoop`
(`internal/mailjmap/push.go:38`) and `idleLoop`
(`internal/mailimap/idle.go:33`) run unconditionally for the
lifetime of the backend's `connCtx`. The connections do not pause
on blur, the EventSource SSE stream stays open, and IDLE keeps
its 9-minute refresh cadence.

**Finding D (P2 — audit-plan drift).** The audit-plan describes a
behavior poplar does not have. There is no resume path, therefore
no double-pump hazard, and no stale-Cmd risk on focus regain.
Two valid responses:

- Update `docs/poplar/audit-plan.md` §"Phase C" to drop the
  ReportFocus focus item from the binding contract; restore it
  only if poplar adopts blur-driven IDLE/push pause in a future
  pass.
- Add the pause/resume capability as a deliberate scope (energy
  / network-egress savings on a backgrounded terminal). Out of
  Audit C scope; would be a fresh feature pass.

Recommendation: apply the audit-plan edit inline this pass. The
feature is not on the roadmap and the focus item is misleading to
future audits.

## 4. `v.ProgressBar` lifecycle

`frameProgressBar` (app_view.go:16-30) reads atomic counters
every frame and returns nil when no source is active, so the
OSC-9;4 "remove progress bar" terminal sequence fires
deterministically once `attachInFlight`, `burstTotal`, and
`syncInFlight` all reach zero. The error-decay path is fully
time-bounded via `progressErrorUntil` and tested
(app_view_test.go:60).

The attachment path defers `EndAttachmentDownload` against
`BeginAttachmentDownload` inside the cache layer
(`internal/cache/attachments.go:113-114`). The drainer resets
`burstTotal=0`/`burstDone=0` when its pickup query returns
`sql.ErrNoRows` (drainer.go:109-112) — every drained burst lands
back at the zero state.

**Finding C (P0 — apply inline this pass).** `BeginSync` and
`EndSync` in `internal/ui/account/cmds.go:34-36` and
`cmds.go:62-64` run as sequential statements rather than a
`defer`. The cache call between them — `c.SyncFolders` /
`c.SyncFolder` — is not expected to panic, but the surrounding
contract is: any panic between the two calls strands
`syncInFlight` at >0, the next `frameProgressBar` reports
`sync=true` indefinitely, and the terminal's OSC-9;4 indeterminate
bar never clears. The attachment site already uses `defer` for
exactly this reason. The fix is mechanical (move the End call
under `defer` of the Begin call) and is applied as part of this
pass.
