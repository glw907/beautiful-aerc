# Audit E — specified vs. assumed

Phase E of `docs/poplar/audit-plan.md`. Read-only walk of every
ADR in `docs/poplar/decisions/` (currently 0001–0224) against the
question:

> Was this decision *chosen* — surfaced as a tradeoff, brainstormed,
> deliberately picked — or *defaulted* — Claude proposed it inside
> a plan, the user accepted, and it ossified without being
> interrogated?

The premise: bugs that survive structural and feature audits live
at the decision layer. LLMs default to sensible-looking choices
that are right 80% of the time and silently wrong in the
remaining 20%. Unquestioned defaults compound across passes.

## Rubric

Three tags per ADR:

- **chosen** — Context section surfaces a real tradeoff against a
  named alternative, *or* the conversation history shows the user
  picked between candidates. Most lipgloss / bubbletea / Charm-
  stack decisions land here (chosen against aerc-fork or
  hand-rolled alternatives).
- **defaulted-and-still-right** — The ADR reads as a foregone
  conclusion (Context shorter than Decision, one-sentence
  rationale, "the obvious choice", "X is idiomatic", no named
  alternative), but the alternative I would have picked given
  the chance is still no better than what's there. Write the
  alternative anyway — if I can't articulate one, that's its own
  finding.
- **defaulted-and-wrong** — Same shape, but with hindsight a
  different choice would be measurably better. These are the
  findings.

Suspect markers (audit-plan §"Phase E"):
- "X over Y" framing whose rationale is one sentence
- "we chose X because it's idiomatic"
- "the obvious choice"
- Context section shorter than Decision section
- No named alternative
- Single-paragraph ADRs with no Consequences exploration

## Walk surface

- `docs/poplar/decisions/0001..0224.md` — every ADR
- `docs/poplar/decisions/INDEX.md` — themed map (read first to
  group ADRs)
- Cross-reference against current code state where a finding
  depends on whether the decision still binds the implementation

## Walk strategy

The themed groups in INDEX.md are the natural unit. Walking
chronologically would mix themes; walking by theme lets the
rubric apply consistently within a subsystem. Where a theme
spans many ADRs (mail stack, Elm architecture, cache I/II/III)
the cluster gets one entry with per-ADR notes if any deviate.

The walk lives in this plan doc; the outcome lands in ADR-0225.

## Out of scope

- Re-deciding settled ADRs. Findings produce a one-line
  counterfactual; remediation, if any, runs as a follow-up pass.
- ADRs already audited by Audits A/B/C/D — those audits covered
  *whether the code matches the ADR*. This audit covers *whether
  the ADR's decision was the right one to make in the first place*.
- Voice / human-tells lensing of ADRs themselves. Phase Final
  carries that lens; Phase E asks only about the decision content.

## Findings

Twelve `defaulted-and-wrong` items. Classified per audit-plan
§"Audit mechanics": P0 (silent data loss / credential leak /
unrecoverable), P1 (behavioral, queued for remediation pass),
P2 (noted only, no remediation queued).

### F1 — ADR-0003 not marked superseded (P2)

ADR-0003 ("External editor only") was contradicted by ADR-0034
("Inline compose, no terminal takeover") but its frontmatter
still reads `status: accepted`. A future audit walking ADRs by
status will hit a contradictory "accepted" pair. Fix: set
ADR-0003's frontmatter to `status: superseded by 0034` and link
in its Consequences section.

### F2 — ADR-0091 movepicker arrow-key navigation breaks vim-first consistency (P1)

ADR-0091 keeps `j`/`k` available as filter input by using `↑`/`↓`
for navigation in the move picker. Sidebar search (ADR-0064)
solves the same conflict via `Tab` mode toggle without giving up
vim navigation. The carve-out is acknowledged in the ADR as a
"documented exception"; documented exceptions to vim-first that
have a working sibling pattern are findings. Fix: align
movepicker with the sidebar-search pattern (Tab cycles
filter/nav) — `j`/`k` work in nav mode.

### F3 — ADR-0108 XOAUTH2 token caching gap (P2)

`password-cmd` runs on every dial with no in-memory grace window.
ADR-0193 + 0220 made native OAuth (with `mailauth.Token` caching
+ keyring/age-file token store) the canonical path; the
`password-cmd`-XOAUTH2 legacy lane retains the per-dial round-
trip. The legacy lane is sunsetting, but until it's removed a
5-minute grace cache on the resolved token would eliminate
redundant `oauth2l` invocations on transient reconnect. Marked
P2 because the path is legacy and small.

### F4 — ADR-0158 outbox payload unbounded (P1)

`outbox.payload` stores assembled MIME bytes with no per-account
cap and no per-row cap. A stalled multi-MB Append (e.g., a large
attachment to a disconnected IMAP server with `MaxAttempts = 0`)
sits in the cache forever; nothing prunes by size. Fix: a
`[cache] max-outbox-bytes` config knob (similar to ADR-0122's
`max-size` for bodies; default unlimited preserves backward
compatibility) plus a per-row soft cap surfaced as a config
validation error before queuing.

### F5 — ADR-0184 hand-rolled date parser vocabulary will rot (P2)

`compose.ParseSchedule` is ~175 lines of hand-rolled English
keyword + offset parsing. The ADR names `araddon/dateparse` as
"the strongest Go option" and rejects it on dep-cost grounds.
The vocabulary will accrue gaps every time a user types something
the parser doesn't grok ("end of month", "after lunch", etc.);
vendoring `araddon/dateparse` for the natural-language path while
keeping the hand-rolled keyword presets gives the full English
parser at one extra dep. P2 because the failure mode is "schedule
button does nothing"; not silent corruption.

### F6 — ADR-0193 OAuth: BYO-client only, no device-code fallback (P1)

Loopback PKCE requires the user to register their own Google
Cloud / Azure OAuth client. Terminal power-users on remote SSH
sessions, in containers, or behind NAT cannot complete the
loopback flow; device-code (RFC 8628) covers all these cases
and is supported by both Google and Microsoft. The ADR cites
Google CASA display-name verification as the reason device-code
was rejected — CASA gates maintainer-distributed clients, not
user-driven device-code flows. Fix: keep loopback PKCE as
default, add device-code as a fallback selectable in the wizard
when loopback fails or the user opts in. Scope is wizard +
`mailauth` + an additional `Authorize` mode; non-trivial.

### F7 — ADR-0188 FTS5 stored-content table duplicates body text on disk (P2)

The ADR chose stored-content over contentless-FTS5 to avoid the
contentless `DELETE` idiom (INSERT with null values). At 33k+
cached messages the duplicated plaintext is a measurable on-disk
cost users will notice (Audit D Phase D Focus 6 already audited
attachment blob shape; this is the search-side analog). The
contentless workaround is ~10 lines of helper. Reclassifying to
contentless is a schema migration (v14) and a `fts.go` rewrite.
P2 because it's storage-only, not behavioral; flagged for
ROADMAP rather than 38.1 if the team picks it up.

### F8 — ADR-0066 markdown body width 72 hardcoded (P2)

72 is the standard. Users on wide terminals would prefer 80 or
100; users on narrow phones-over-SSH would prefer 56. A `[ui]
body-width` config knob (default 72) is one config field. P2 —
small and self-contained.

### F9 — ADR-0085 long-bare-URL footnoting threshold 30 cells (P2)

`example.com/login?token=abc` is 30 cells and gets footnoted;
that's the threshold's first failure mode. Bumping to 50
preserves more short query-param URLs while still trapping
genuinely wrapped monsters. The ADR itself notes the feature is
a no-op until BACKLOG #22 lands, so the threshold is currently
a hypothetical; revisit when #22 lands. P2.

### F10 — ADR-0135 zero-length attachment results not cached (P2)

Every attachment-free message hits the backend on viewer-open.
A `messages.has_attachments BOOL` column eliminates the round-
trip. The ADR notes this as a backlog item — that's the tell
that the no-cache default was wrong. Small schema bump. P2.

### F11 — ADR-0147 catkin word-level undo coalescing (P2)

Intra-word coalescing is workable for prose but Ctrl+K link
skeletons, address chip edits, and tidy-replace blocks all want
finer granularity. The ADR has no named alternative — undo
granularity is presented as a foregone choice. P2; no clear
remediation candidate yet.

### F12 — ADR-0164 draft last-write-wins shipped with no UI signal (already addressed)

The agent surfaced this as a finding; ADR-0165 already added
`ErrDraftSuperseded` + banner surfacing. Not a current finding,
recorded here so a future audit doesn't re-surface it.

## Borderline cases — defaulted-still-right with no articulable alternative

Per the audit-plan: "For every *defaulted-and-still-right* ADR,
write the alternative you would have picked given the chance. If
you can't articulate one, that's its own finding."

Range 1: 0004, 0015, 0024, 0026, 0039, 0054.
Range 2: 0063, 0074, 0097, 0100, 0102.
Range 3: 0122, 0124, 0131, 0137, 0153, 0172.
Range 4: 0182, 0196, 0204, 0205, 0209.

22 ADRs total. Most are small (single-paragraph utility ADRs,
mechanical bump records, process notes). None reach P1: an ADR
with no articulable alternative is mostly evidence the ADR
itself was overcommitted to a small choice, not that the choice
was wrong. The pattern is recorded — *if Phase Final wants to
prune ADRs that should not have needed ADRs, this list is the
candidate set*.

## Disposition

12 findings: 0 P0, 3 P1 (F2, F4, F6), 8 P2 (F1, F3, F5, F7–F11),
1 already-addressed (F12).

Per audit-plan, P0/P1 land in a remediation sub-pass. Pass 38.1
queues F1 (cheap hygiene fix bundled with the P1s), F2, F4, and
F6's loopback-PKCE-stays-default + device-code-fallback wiring.

F6's scope (wizard + mailauth + an Authorize-mode addition) is
the largest item; if the controller decides 38.1 has too much
surface, F6 can split into its own pass.

P2 items: F5 (date parser), F7 (FTS5 contentless), F8 (body
width knob), F9 (URL threshold), F10 (has_attachments column),
F11 (undo granularity) — left for the team to log against
BACKLOG/ROADMAP as appetite allows. F7 specifically is large
enough to be a ROADMAP project rather than a backlog item.
