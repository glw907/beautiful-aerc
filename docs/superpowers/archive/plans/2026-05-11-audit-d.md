## Focus 1 — Schema migration ladder

Walked v1 → v12 in `internal/cache/schema.go`. Each step is single-
purpose and runs in its own tx via `applyMigrationsTo`. The v9
outbox rebuild (rename → recreate → reinsert with `__contacts__`
sentinel collapse) is the largest; no inbound FK references on
`outbox`, so the rename is safe. The v10 index swap re-creates
`outbox_pickup` with `(scheduled_for, next_eligible_at, id)`.

**v11 backfill gap (Finding F3, P1).** `migrateV11` inserts one
`messages_fts` row per existing message with the header columns
populated but `body = ''`. The Backfiller only writes bodies to FTS
via `storeBody`, which fires on `FetchBody` cache misses — its work
query is `WHERE b.bytes IS NULL`. A user upgrading from a pre-v11
cache where bodies are already populated will therefore get no body-
search hits for those messages until each is manually re-fetched
(eviction + new fetch). The fix is to extend the v11 migration to
extract plaintext from already-cached bodies and populate the body
column in the same tx (or pair it with a one-shot post-migration
backfill driven by the Backfiller).

## Focus 2 — Transactional boundaries

`QueueOp` (Move/Flag/Destroy): single tx — message resolve →
`applyOptimisticTx` (ui_flags / ui_hide) → outbox INSERT. ✓
`insertFolderOp` (Send/Append/PushDraft/ContactPut/ContactDelete):
single tx — outbox INSERT with payload + scheduled_for + draft_id.
✓ `QueueContactPut`/`QueueContactDelete`: upsert/delete contact row
+ outbox INSERT in one tx. ✓ `ApplyChangeset` (CardDAV apply): wraps
remove + add + token update. ✓ `RetryOp` / `DiscardOp` / `CancelOps`:
all single tx, status-precondition guarded. ✓

Drainer execute/finalize is *not* a single tx by design:
`markExecuting` is a single-statement update; dispatch runs against
the backend uncontended; `finalizeSuccess` or `finishOp` writes the
terminal state in its own tx. The crash window between
`markExecuting` and the terminal write is covered by
`recoverExecuting`:

- Idempotent kinds (Move, Flag, Destroy, ContactPut, ContactDelete)
  → reset to pending and replay.
- Non-idempotent kinds (Send, Append, PushDraft) → OpConflict
  `crashed-mid-execute`; user discards.

ContactPut/ContactDelete being grouped with idempotent kinds is
acceptable: PUT/DELETE with `If-Match` is safe to replay — a stale
ETag returns 412 → routes to OpConflict `precondition-failed`.

## Focus 3 — FTS5 consistency

`writeFTSHeadersTx` fires from `upsertMessages` (which itself runs
inside `a.tx`). ✓ `writeFTSBodyTx` fires from `storeBody`. ✓
`messages_fts` is a regular FTS5 table; DELETE+INSERT preserves the
unrelated columns (read-modify-write).

**Orphan FTS rows on message delete (Finding F2, P2).**
`DELETE FROM messages WHERE id = ?` (drainer `finalizeSuccess` →
DestroyArgs) and `DELETE FROM messages WHERE protocol_id IN (...)`
(`applyDelta` for `Removed`) leave the corresponding `messages_fts`
row in place. FTS5 is a virtual table — no FK cascade reaches it.
The search query is `JOIN messages m ON m.id = fts.rowid` (inner
join), so orphan rows are filtered out at read time and never
return false hits. The cost is storage only. Classified P2 (no
behavioral effect, storage bloat is bounded by message-deletion
rate). Fix is mechanical: explicit `DELETE FROM messages_fts WHERE
rowid IN (...)` paired with each `DELETE FROM messages` site, in
the same tx.

**Orphan recipient rows on message delete (Finding F1, P1).**
`message_recipients` has no FK to `messages` (v8 schema: `message_uid
INTEGER NOT NULL` with no `REFERENCES messages(id) ON DELETE
CASCADE`). The autocomplete query in `suggestQuery` reads
`message_recipients` and joins to `contacts`/`contact_emails`
without touching `messages`, so orphan recipients keep contributing
to recency-decayed ranking for addresses the user has deleted every
message from. Visible behavioral effect (autocomplete bias). The
fix is either an explicit `DELETE FROM message_recipients WHERE
message_uid IN (...)` in both delete paths, or a schema migration
adding `REFERENCES messages(id) ON DELETE CASCADE` to the column.
Schema fix is cleaner (defense in depth, future-proof against
new message-delete sites).

## Focus 5 — UIDVALIDITY re-key + IMAP scan-and-diff

JMAP `Changes` returns `mail.ErrCannotCalculateChanges` on the
`cannotCalculateChanges` server-side condition; cache `SyncFolder`
routes that into `reAnchor`. `reAnchor` promotes pending/executing
outbox rows for the folder to `OpConflict anchor-lost`, clears the
folder's `message_mailboxes`, and nulls `sync_token`. ✓

**IMAP UIDVALIDITY change goes undetected (Finding F4, P1).**
`mailimap/changes.go` comments claim "UIDVALIDITY change returns
mail.ErrCannotCalculateChanges so the cache re-anchors" and the
SyncToken layout reserves bytes 0–3 for `uidvalidity`. The
implementation never reads them: bytes 4–11 carry `maxuid`, the
loop diffs against `prevMax` only, and `mail.Folder` carries no
`UIDValidity` field. After a server-side UIDVALIDITY change (UID
reset to 1), `cmd.Search(...)` returns smaller UIDs than `prevMax`,
the `n > prevMax` filter excludes everything, `newMax` is stuck at
the old high-water value, and the cache silently diverges from the
server. The user can only recover by deleting the per-account
cache directory.

The fix spans `internal/mail/` (add `UIDValidity uint32` to
`mail.Folder`), `internal/mailimap/{folders,changes}.go` (capture
UIDVALIDITY from `SELECT`/`EXAMINE`, encode into SyncToken bytes
0–3, compare against the stored value, return
`mail.ErrCannotCalculateChanges` on mismatch). Pre-beta IMAP user
count is zero (Fastmail/JMAP is the current account); the
divergence is currently silent only because no IMAP backend is in
production. Classified P1, queued for Pass 37.1.

`reAnchor` itself is sound — promotes outbox rows, unlinks
mailbox memberships, nulls sync token, all in one tx. Messages
left with zero memberships persist in `messages` (and FTS,
`message_recipients`); next baseline pull re-links them by
`protocol_id`. The orphan storage cost overlaps with F1/F2.

## Focus 6 — File-on-disk shape

Attachment bytes are stored inline as SQLite `BLOB`
(`attachments.bytes`); there is no out-of-DB persistence to leak.
`DELETE FROM messages` cascades to `attachments` via `ON DELETE
CASCADE`. ✓ The "chunked blob / path-keyed" question raised in
the audit plan does not apply to the current shape.

## Focus 7 — Drainer conflict matrix (state side)

Every dispatch outcome lands a terminal status:

| Outcome                      | Status        | Error kind                 |
|------------------------------|---------------|----------------------------|
| `nil`                        | OpDone        | —                          |
| `contacts.ErrAuth`           | OpConflict    | `auth-failure`             |
| `contacts.ErrPreconditionFailed` | OpConflict| `precondition-failed`      |
| `contacts.ErrNotFound`       | OpDone        | (idempotent)               |
| `mail.ErrAuth`               | OpConflict    | `auth-failure`             |
| `mail.ErrNotFound`           | OpDone        | (idempotent)               |
| `ErrDraftSuperseded`         | OpDone w/note | (advisory banner)          |
| transient + attempts < max   | OpFailed      | `transient` + next_eligible_at |
| transient + attempts >= max  | OpConflict    | `max-attempts-exceeded`    |
| args decode failure          | OpConflict    | `args-decode`              |
| crash mid-execute (recovery) | OpConflict (non-idempotent) / OpPending (idempotent) | `crashed-mid-execute` |

`nextOutboxRow` picks only `pending` / `failed`, and `failed` is
gated by `next_eligible_at <= now`. `OpConflict` is terminal until
`RetryOp` or `DiscardOp`. No undead retry-loop path. ✓

`MaxAttempts = 0` bypasses the cap (infinite retry); the default
is 10. Documented as a config knob, not a hazard.
