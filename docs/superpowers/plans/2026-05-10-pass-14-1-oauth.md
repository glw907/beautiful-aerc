# Pass 14.1 — OAuth subsystem (Gmail / Outlook IMAP)

> **Stub plan.** Locks in shape; full task breakdown brainstormed at
> the start of 14.1 once Pass 14's wizard scaffold is in hand.
> Companion to BACKLOG #42.

**Goal:** Wire native OAuth for Gmail / Outlook IMAP onto Pass 14's
`CredentialStrategy` seam. User registers their own OAuth client
(BYO client ID) in Google Cloud / Azure Portal once; poplar handles
the browser consent flow, refresh-token storage, and proactive
refresh before access-token expiry. `password-cmd` stays as the
fallback for self-hosted IMAP, Fastmail JMAP, and users who prefer
their own secret manager.

**Why BYO client ID and not a maintainer-verified client.** Google's
restricted-scope verification (Gmail IMAP qualifies) requires an
annual third-party CASA security audit. Not feasible for solo OSS.
aerc's pattern fits poplar; Thunderbird/K-9's maintainer-owned path
is Mozilla-staffed and out of reach. Microsoft is somewhat lighter
but still requires publisher verification and is left to BYO for
parity.

**Architecture.** Three layers, each cleanly testable:

- `internal/mailauth/` (UI-free) gains an `OAuth` subsystem:
  `Client` (config + token-store handle), `Authorize(ctx) error`
  (drives the consent flow), `Token(ctx) (string, error)` (returns a
  valid access token, refreshing if needed). Wraps
  `golang.org/x/oauth2`.
- `internal/cache/oauth.go` (or a sibling under `internal/mailauth/`,
  TBD at brainstorm) provides token storage. Refresh tokens are
  the sacred-data class — encrypt at rest via OS keyring
  (`99designs/keyring` candidate; final choice at brainstorm).
- `internal/wizard/strategy.go` gains `oauthStrategy` implementing
  the `Strategy` interface laid down in Pass 14. Wizard runs
  `Authorize` synchronously (blocking step with live status), then
  the standard `Probe` step continues.

**Tech stack.** `golang.org/x/oauth2` (stdlib-adjacent, well-trodden);
`99designs/keyring` candidate for token storage (final choice at
brainstorm — alternatives: `zalando/go-keyring`, hand-rolled
age-encrypted file at `$XDG_DATA_HOME/poplar/oauth/<account>.age`);
loopback-redirect server for the consent flow (stdlib `net/http`).
No device-code flow in v1 — the loopback flow is universally
supported by Google + Microsoft and doesn't require a verified
display name. Reconsider at brainstorm if SSH-only-user feedback
arrives.

**Spec:** `docs/superpowers/specs/2026-05-10-pass-14-1-oauth-design.md`
— **to write at the start of 14.1.** Pass 14's spec already
sketches the seam at §"Out-of-pass — Pass 14.1 preview" (line 515).

## Settled (do not re-brainstorm)

- BYO client ID is the strategy. Maintainer-verified is out of
  scope for v1 (per BACKLOG #42 framing).
- `password-cmd` stays as a parallel auth path for non-OAuth
  accounts. OAuth doesn't replace it.
- Pass 14's `CredentialStrategy` enum is the dispatch seam; no
  cross-cutting refactor of the existing IMAP/JMAP auth path.
- Token-refresh failures surface as `mail.ErrAuth`; the existing
  cmd/idle goroutine reconnect logic re-resolves and retries
  (mirrors the `password-cmd` resolver path).

## Open at brainstorm

- **Keyring library.** `99designs/keyring` (broader OS coverage,
  more deps) vs. `zalando/go-keyring` (Linux/macOS/Windows only,
  thin) vs. age-encrypted file (no system-keyring dependency, fully
  portable, but requires user to manage one more passphrase).
- **Token-store layout.** One file/keyring entry per account
  (matches the existing per-account cache shape) vs. one combined
  store (simpler atomic writes).
- **Consent-flow recovery.** What happens when the user cancels in
  the browser, or the loopback callback never fires (firewall,
  Docker, SSH-with-no-tunneling)? Timeout + retry vs. fall back to
  device-code flow vs. surface an "edit the helper script
  yourself" escape hatch.
- **Refresh on idle disconnect.** When IMAP IDLE drops with
  `AUTHENTICATIONFAILED` and `Token()` refresh succeeds, do we
  re-authenticate the existing connection or tear it down and
  redial? Aerc tears down; cleaner state but a small reconnect
  blip.
- **First-time setup docs.** A walkthrough doc for the BYO
  registration step is part of this pass (Google Cloud Console +
  Azure Portal). Lives at `docs/poplar/oauth-setup.md`.

## Rough task shape (refine at brainstorm)

1. `internal/mailauth/oauth.go`: `Client`, `Authorize`, `Token`,
   refresh loop. Tests use a fake token endpoint.
2. Token storage: keyring or age-file impl per brainstorm decision.
   `Store` interface so tests use an in-memory fake.
3. Loopback callback server: `net/http` listener on `127.0.0.1:0`
   (kernel-assigned port), `state` parameter check, single-shot
   handler.
4. `internal/config/oauth.go`: `[[account.oauth]]` decode
   (client_id, client_secret, scopes, auth_url, token_url, redirect
   port range), validation, integration with the existing provider
   preset machinery (`gmail` / `outlook` presets fill the URLs).
5. `internal/wizard/oauth_strategy.go`: `oauthStrategy` impl,
   wizard sub-screen for Authorize with live status.
6. `internal/mailimap/auth.go`: route XOAUTH2 token resolution
   through `mailauth.Token` when the account has an OAuth config;
   `password-cmd` path unchanged. Refresh-on-`ErrAuth` in the cmd
   and idle goroutines.
7. `docs/poplar/oauth-setup.md`: BYO registration walkthrough for
   Gmail and Outlook, with screenshots.
8. Tests: oauth_test.go (mock token endpoint), wizard sub-screen
   test, integration test against the existing `mailimap.Probe`
   surface.
9. ADR-0190 (or next): OAuth subsystem decisions — BYO rationale,
   keyring library choice, loopback flow choice, token-store
   layout.
10. Invariants update + INDEX.md row + plan/spec archive +
    STATUS pivot to Pass 15.

## Out-of-pass

- Maintainer-verified OAuth client (Google CASA audit + Microsoft
  publisher verification). Not in v1; revisit if/when the project
  grows funding to absorb the audit cost.
- Device-code flow for SSH-without-tunneling users. Add only if
  loopback-flow feedback identifies a real cohort that can't make
  it work.
- OAuth for JMAP. Fastmail uses long-lived API tokens; no current
  consumer wants OAuth on JMAP.
