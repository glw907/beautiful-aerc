- [ ] **#42** Native OAuth for Gmail / Outlook IMAP (BYO client ID) `#feature` `#poplar` `#v1` `#config` *(2026-05-10)* — **bundle with #27 first-run wizard**
  Today `internal/mailimap/auth.go` resolves the XOAUTH2 access token from `password-cmd` once at Connect and never refreshes — Gmail/Outlook tokens expire on ~1h timers, so any long-lived session hits `AUTHENTICATIONFAILED` mid-IDLE with no recovery path. The fix isn't "re-invoke password-cmd on auth failure"; the better UX is **native OAuth with BYO client ID**. Mainstream clients (Thunderbird, K-9) ship maintainer-verified OAuth clients, but Google's restricted-scope verification (Gmail IMAP qualifies) requires an annual third-party CASA audit that's not feasible for solo OSS. **aerc's pattern fits poplar**: user registers their own OAuth client in Google Cloud / Azure Portal (one-time, 5–10 min), pastes client ID + secret into config, then poplar handles the browser consent flow, refresh-token storage (encrypted at rest or via `go-keyring`), and proactive refresh before access-token expiry. `password-cmd` stays as the path for self-hosted IMAP, Fastmail JMAP (API token, no OAuth), and users who prefer their own secret manager. Bundles with #27 because the first-run wizard is the natural surface for the OAuth flow ("Sign in with Google" button) and because the wizard's mental model breaks if Gmail/Outlook setup means "go write a helper script." Touches `internal/mailauth/` (OAuth client + refresh loop), `internal/mailimap/auth.go` (cmd/idle goroutines re-resolve on `mail.ErrAuth`), `internal/config/` (`[[account.oauth]]` block with client_id / client_secret / token-store path), `internal/cache/` (refresh token storage + encryption), the wizard flow itself, and the OAuth-setup docs the user follows for BYO registration.

- [x] **#25** ~~Some emails render with no body text~~ `#bug` `#poplar` *(2026-04-29)* (closed 2026-04-29)
  Resolved 2026-04-29: root cause was a missing `_ "github.com/emersion/go-message/charset"` blank import in `internal/ui/cmds.go`. go-message's charset registry only carries UTF-8 by default; MIME parts declaring `charset="iso-8859-1"` (Outlook/Exchange default) failed to decode and `mr.NextPart()` errored on the first part, exiting the extraction loop with both plain and html unset. - [ ] **#36** List-Unsubscribe one-click (RFC 8058) `#feature` `#poplar` `#v1` `#viewer` *(2026-05-05)* — **scheduled: Pass 9.3**
  Mainstream clients (Thunderbird, Apple Mail, Gmail, Fastmail) all expose an unsubscribe action on rows whose messages carry a `List-Unsubscribe` header. mutt and aerc have nothing built-in. RFC 2369 defines the header shape: `List-Unsubscribe: <mailto:...>, <https://...>`. RFC 8058 layers one-click semantics: when `List-Unsubscribe-Post: List-Unsubscribe=One-Click` is present, a single empty-body HTTP POST to the URL unsubscribes silently. For poplar: parse both headers, show a chip below the header panel when present, bind capital `U` to unsubscribe with a confirmation prompt (users expect an "are you sure" here even though the spec doesn't require it). RFC 8058 path issues an HTTP POST and surfaces a toast on success/failure. RFC 2369 mailto path enqueues a Send op via the cache outbox (same plumbing as user-composed mail). URL-only fallback opens a browser via the existing `URLOpener` seam (ADR-0128). Touches `internal/mail/types.go` (MessageInfo gains `ListUnsubscribe` + `ListUnsubscribePost` wire fields), viewer chip row, `internal/ui/keys.go`, a small `internal/listunsub/` helper for the POST. ~6 tasks.

- [ ] **#35** Outbox delivery controls — undo send + schedule send `#feature` `#poplar` `#v1` `#compose` *(2026-05-05)* — **scheduled: Pass 9.2 (after 9.5)**
  Both ride the cache outbox landed in Pass 9g — the same row, the same drainer, distinguished only by a `not_before` timestamp. **Undo send:** hold the row for `[ui] undo-send-window = 10s` (default) before the drainer dispatches. Touches `internal/cache/outbox.go` (drainer skip logic, `not_before` column via schema migration), `internal/ui/compose_tab.go` (schedule picker + send-with-undo flow), `internal/ui/status.go` (countdown), `internal/ui/sidebar.go` (Outbox virtual folder). ~8 tasks.

- [ ] **#33** Drafts persistence (compose) `#feature` `#poplar` `#v1` `#compose` *(2026-05-05)* — **scheduled: Pass 9h.5 (immediately after 9h)**
  Compose foundation has the `Draft` value type (ADR-0156) but no persistence — switching tabs mid-compose loses work. Two patterns from prior art: (a) **server-side**, APPEND to the Drafts mailbox on save and replace on edit (Thunderbird, Apple Mail, aerc, Fastmail) — drafts visible across devices, costs UID churn on every keystroke-batch save; (b) **cache-local**, store rows in a `drafts` SQLite table that never round-trips until send (mutt's `postpone-message`, simpler). Recommend (a): poplar already has the IMAP APPEND path (Pass 9f) and JMAP `Email/import` to the Drafts mailbox role, and cross-device drafts are a real user expectation now that mobile + desktop is the norm. Auto-save every ~5 seconds and on tab-switch / quit. The Drafts folder in the sidebar lists them; selecting one opens ComposeTab with the body restored. Pass 9h ships ComposeTab with a simple "discard?" prompt on close; this pass adds the persistence layer immediately after so users don't live with the "lost on Esc" gap for long. Touches `internal/cache/` (drafts metadata + body cache), `internal/mail/` (Append already exists per ADR-0157 — verify it routes correctly to the Drafts role mailbox), `internal/ui/compose_tab.go` (auto-save timer, restore-from-Draft path), sidebar handling for the Drafts folder. ~7 tasks.

- [ ] **#32** Email signatures + multiple identities `#feature` `#poplar` `#v1` `#compose` *(2026-05-05)* — **scheduled: Pass 9.4 (after 9.1)**
  **Signatures.** Per-account-or-per-identity static text appended to outbound mail. Design surface: per-account vs. per-identity placement; plain-text vs. markdown body (and how the signature flows through `multipart/alternative` HTML rendering in `compose.AssembleMIME`); reply/forward placement (above quote, below quote, at end); the RFC 3676 `-- \n` delimiter (Fastmail and most clients honor it for visual separation and for "trim signature" features); materialized into the editable Draft body at compose-open time (Fastmail/TB pattern — visible, editable, removable per-message) vs. appended at MIME-assembly time (invisible, uniform). Recommend materialize-at-open with `-- \n` delimiter — matches user expectations from every mainstream client. **Identities.** Multiple From addresses per account, each with its own signature and optional Reply-To. Prior art: Thunderbird treats identities as first-class per-account (Edit Identity dialog); aerc handles multi-identity by declaring multiple `[account]` blocks per real account (works but bloats config); Apple Mail uses send-from aliases tied to the account; Gmail's "Send mail as" verifies aliased addresses; Fastmail allows per-identity signatures including HTML. Recommend `[[account.identity]]` sub-blocks under `[[account]]`, each with `name`, `email` (the From address), optional `signature` / `signature-file`, optional `reply-to`. First identity is the default. ComposeTab shows an identity selector when an account declares >1; replies pick the identity matching the parent's To address. Brainstorm before coding. Touches `internal/config/` (`[[account.identity]]` decode + validation), `internal/compose/` (`Draft.Identity`, `Seed*` consults the identity for the From + signature), `internal/ui/compose_tab.go` (identity picker, reply identity selection).

- [ ] **#28** CONDSTORE-aware IMAP ChangeTracker `#improvement` `#poplar` *(2026-05-02)* — **scheduled: post-8.4c, after profiling**
  Current `internal/mailimap/changes.go` is scan-and-diff (`UID SEARCH ALL`, diff against prior maxuid encoded in the SyncToken). Modified UIDs are always nil, so flag-only changes round-trip through `Backend.FetchHeaders` for the affected set. Replace with `UID FETCH 1:* CHANGEDSINCE <modseq>` per RFC 7162, plus the CONDSTORE assertion at `finishConnect` (NOMODSEQ → fail Connect with a clear error). SyncToken is forward-compatible: bytes 0-3 reserved for uidvalidity, bytes 4-11 hold maxuid; add a third field (modseq) by re-laying the 12-byte token. Wire VANISHED detection so Removed UIDs aren't best-effort. ADR-0120.
